## Common Performance Issues

- **N+1 queries:** Loading related data in loops
- **Over-fetching:** Loading all columns when you need a few
- **Cartesian explosion:** Multiple Includes causing data duplication
- **Client evaluation:** Processing data in memory instead of database

## Projection (Select Only What You Need)

Project only the columns you need to avoid over-fetching. The left example loads entire entities then projects in memory (inefficient); prefer projecting in the query so SQL only returns required columns.

```csharp
// ❌ Bad - loads entire entity
var products = await context.Products.ToListAsync();
var names = products.Select(p => p.Name);

// ✅ Good - only loads Name column
var names = await context.Products
    .Select(p => p.Name)
    .ToListAsync();

// ✅ Project to DTO
var dtos = await context.Products
    .Select(p => new ProductDto { Id = p.Id, Name = p.Name })
    .ToListAsync();
```

## No-Tracking for Read-Only

No-tracking queries skip change tracking overhead. Use `AsNoTrackingWithIdentityResolution()` when you still need stable identity for included entities.

```csharp
// ✅ No tracking overhead for read-only queries
var products = await context.Products
    .AsNoTracking()
    .ToListAsync();

// ✅ No tracking with identity resolution
var products = await context.Products
    .AsNoTrackingWithIdentityResolution()
    .Include(p => p.Category)
    .ToListAsync();
```

## Compiled Queries

Compile frequently-used queries to avoid expression tree re-processing and improve performance for repeated executions.

```csharp
// Pre-compile frequently used queries
private static readonly Func<AppDbContext, int, Task<Product?>> GetProductById =
    EF.CompileAsyncQuery((AppDbContext context, int id) =>
        context.Products.FirstOrDefault(p => p.Id == id));

// Usage (faster for repeated calls)
var product = await GetProductById(context, 42);
```

## Raw SQL and Stored Procedures

Use raw SQL for very complex queries or to reuse existing stored procedures; prefer parameterized or interpolated APIs provided by EF Core to avoid SQL injection.

```csharp
// Raw SQL for complex queries
var products = await context.Products
    .FromSqlRaw("SELECT * FROM Products WHERE Price > {0}", minPrice)
    .ToListAsync();

// Interpolated (SQL injection safe)
var products = await context.Products
    .FromSqlInterpolated($"SELECT * FROM Products WHERE Price > {minPrice}")
    .ToListAsync();

// Execute non-query
await context.Database
    .ExecuteSqlRawAsync("UPDATE Products SET Stock = 0 WHERE Discontinued = 1");
```

## Bulk Operations

Avoid per-entity saves in loops—batch inserts/updates/delete with AddRange or the bulk APIs (EF Core 7+) to reduce round trips to the database.

```csharp
// ❌ Slow - individual inserts
foreach (var product in products)
{
    context.Products.Add(product);
    await context.SaveChangesAsync();  // N database calls!
}

// ✅ Better - batch insert
context.Products.AddRange(products);
await context.SaveChangesAsync();  // 1 database call

// ✅ Best for large sets - EF Core 7+ bulk operations
await context.Products
    .Where(p => p.CategoryId == oldCategoryId)
    .ExecuteUpdateAsync(s => s.SetProperty(p => p.CategoryId, newCategoryId));

await context.Products
    .Where(p => p.IsDeleted)
    .ExecuteDeleteAsync();
```

## Logging Generated SQL

Log generated SQL to analyze and optimize queries; `EnableSensitiveDataLogging()` shows parameter values but avoid enabling it in production.

```csharp
// In Program.cs
options.UseSqlServer(connectionString)
    .LogTo(Console.WriteLine, LogLevel.Information)
    .EnableSensitiveDataLogging();  // Shows parameter values

// Or use a logger
options.UseLoggerFactory(LoggerFactory.Create(builder => builder
    .AddConsole()
    .SetMinimumLevel(LogLevel.Information)));
```
