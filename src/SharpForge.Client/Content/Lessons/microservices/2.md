## Why Migrate?

Most microservices systems start life as monoliths. That's fine — a monolith lets you explore the domain before committing to boundaries. Migration becomes attractive when the monolith slows teams down: long build times, risky deployments, and inability to scale individual features.

This lesson covers practical strategies for breaking a monolith apart without a risky big-bang rewrite.

## The Strangler Fig Pattern

The safest migration strategy is the **Strangler Fig** pattern. New features are built as microservices alongside the monolith, and existing features are gradually extracted until the monolith can be retired.

## Identifying Service Boundaries

The hardest part of decomposition is deciding **where to cut**. There are several heuristics:

### Business Capabilities

Map services to what the business does, not how the code is structured:

- **Order Management** — placing, tracking, and fulfilling orders
- **Inventory** — stock levels, reservations, warehouse operations
- **Payments** — charges, refunds, invoicing
- **Notifications** — email, SMS, push notifications

### Data Ownership

Each service should own the data it needs. If two modules write to the same tables, they probably belong to the same service — or you need to split the table.

```csharp
// ❌ BAD: Two services sharing the same database table
// OrderService and InventoryService both write to Products table

// ✅ GOOD: Each service owns its data
// OrderService owns OrderItems (with a cached ProductName + Price)
// InventoryService owns Products and StockLevels
```

### Change Frequency

Code that changes together should live together. If the payments team ships weekly but the catalog team ships daily, that's a signal they should be separate services.

## Practical Extraction Steps

### Step 1: Draw the Dependency Graph

Before extracting anything, understand the coupling. Identify which modules call which, and which share database tables.

```bash
# In a .NET solution, use dependency analysis
dotnet tool install -g depgraph
depgraph MyMonolith.sln --output graph.png
```

### Step 2: Pick the Easiest Module

Start with a module that has:

- **Few inbound dependencies** (not many other modules call it)
- **Its own data** (or data that's easy to separate)
- **Clear business boundaries**

Notifications and email are often good first candidates.

### Step 3: Define the API Contract

Before extracting code, define the contract between the monolith and the new service:

```csharp
// Shared contract (e.g., in a NuGet package or OpenAPI spec)
public record SendNotificationRequest(
    string UserId,
    string Channel,     // "email", "sms", "push"
    string TemplateId,
    Dictionary<string, string> Parameters);

public record SendNotificationResponse(
    string NotificationId,
    string Status);
```

### Step 4: Build the New Service

Create a standalone ASP.NET Core service that implements the contract:

```csharp
var builder = WebApplication.CreateBuilder(args);
builder.Services.AddSingleton<INotificationSender, EmailSender>();

var app = builder.Build();

app.MapPost("/api/notifications", async (
    SendNotificationRequest request,
    INotificationSender sender) =>
{
    var id = await sender.SendAsync(request);
    return Results.Ok(new SendNotificationResponse(id, "queued"));
});

app.Run();
```

### Step 5: Redirect Traffic

Update the monolith to call the new service via HTTP instead of its internal code:

```csharp
// In the monolith, replace the direct call:
// _notificationService.Send(...)

// With an HTTP call to the new service:
var response = await _httpClient.PostAsJsonAsync(
    "http://notification-service/api/notifications",
    new SendNotificationRequest(userId, "email", "order-confirmation", parameters));
```

### Step 6: Remove the Old Code

Once the new service is stable and handling all traffic, delete the old notification code from the monolith.

## Common Pitfalls

<div class="warning-box">
    <div class="warning-box-header"><span>⚠️ Watch Out</span></div>
    <ul>
        <li><strong>Distributed monolith</strong> — If every service must deploy together, you just have a harder-to-manage monolith.</li>
        <li><strong>Shared database</strong> — Sharing a database between services creates tight coupling. Plan for data separation.</li>
        <li><strong>Too many services too fast</strong> — Extract gradually. Two or three services are a great start.</li>
        <li><strong>Ignoring data migration</strong> — Moving code is easy; moving data is hard. Budget time for it.</li>
    </ul>
</div>

## Best Practices

- **Migrate incrementally** — one service at a time, not a big-bang rewrite
- **Use an API gateway** from the start to route between monolith and services
- **Define contracts first** — agree on APIs before writing code
- **Automate testing** for both the monolith and the extracted service
- **Monitor everything** — you need to know if the new service is performing well before cutting over fully
