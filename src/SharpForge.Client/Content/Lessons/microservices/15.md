## The Front Door to Your System

Without a gateway, clients must know about every individual microservice: their URLs, ports, and protocols. An **API gateway** provides a single entry point that routes requests to the appropriate backend service, and handles cross-cutting concerns in one place.

## Why an API Gateway?

```
Without Gateway:                    With Gateway:
                                    
Client ──▶ OrderService:5001        Client ──▶ API Gateway ──▶ OrderService
Client ──▶ InventoryService:5002                            ──▶ InventoryService
Client ──▶ PaymentService:5003                              ──▶ PaymentService
Client ──▶ NotificationService:5004                         ──▶ NotificationService
```

## Routing Patterns

### Path-Based Routing

Route by URL path prefix:

```
/api/orders/*       → OrderService
/api/inventory/*    → InventoryService
/api/payments/*     → PaymentService
```

### Header-Based Routing

Route by HTTP headers (e.g., API version):

```
Api-Version: 1  → OrderService v1
Api-Version: 2  → OrderService v2
```

### Aggregation

The gateway can combine responses from multiple services into a single response:

```csharp
// Gateway aggregation endpoint
app.MapGet("/api/order-details/{id}", async (
    Guid id, OrderClient orders, CustomerClient customers) =>
{
    var orderTask = orders.GetAsync(id);
    var customerTask = customers.GetAsync(id);

    await Task.WhenAll(orderTask, customerTask);

    return new
    {
        Order = orderTask.Result,
        Customer = customerTask.Result
    };
});
```

<div class="warning-box">
    <div class="warning-box-header"><span>⚠️ Caution</span></div>
    <p>Keep gateway aggregation simple. Complex business logic in the gateway makes it a bottleneck and a maintenance burden. If aggregation becomes complex, consider a Backend-for-Frontend (BFF) service instead.</p>
</div>

## Backend for Frontend (BFF)

Different clients (web, mobile, IoT) often need different API shapes. A **BFF** is a dedicated gateway per client type:

```
Web App    ──▶ Web BFF    ──▶ OrderService, InventoryService
Mobile App ──▶ Mobile BFF ──▶ OrderService (less data, fewer fields)
IoT Device ──▶ IoT BFF    ──▶ InventoryService (status only)
```

Each BFF tailors the response format and aggregation logic for its client.

## Gateway Anti-Patterns

- **Business logic in the gateway** — the gateway should route and protect, not implement features.
- **Single point of failure** — deploy the gateway with redundancy and health checks.
- **God gateway** — don't let one massive gateway config become unmaintainable. Consider multiple gateways for different domains.

## Best Practices

- Keep the gateway **thin** — routing, auth, rate limiting, and TLS only
- Use **health checks** on backend services so the gateway can route around failures
- Enable **request/response logging** at the gateway for debugging
- Deploy the gateway with **multiple instances** behind a load balancer
- Consider **BFF pattern** when different clients need different API shapes
- Use **YARP** for .NET-native gateway development (next lesson)
