## Let the Framework Wire It Up

Dependency Injection (DI) is a first-class citizen in ASP.NET Core. Instead of creating objects manually, you declare what you need and the framework provides it. This lesson covers how to register services, choose lifetimes, and structure your code for testability.

## What is Dependency Injection?

DI is a design pattern where an object receives its dependencies from an external source rather than creating them itself:

```csharp
// ❌ BAD: Tight coupling — hard to test, hard to change
public class ProductsController : ControllerBase
{
    public IActionResult GetAll()
    {
        var db = new AppDbContext();  // Creates its own dependency
        var products = db.Products.ToList();
        return Ok(products);
    }
}

// ✅ GOOD: Loose coupling — testable, flexible
public class ProductsController : ControllerBase
{
    private readonly IProductService _productService;

    public ProductsController(IProductService productService)
    {
        _productService = productService;  // Provided by DI container
    }

    [HttpGet]
    public ActionResult<IEnumerable<Product>> GetAll()
    {
        return Ok(_productService.GetAll());
    }
}
```

## Registering Services

Services are registered in `Program.cs` using the `builder.Services` collection:

```csharp
var builder = WebApplication.CreateBuilder(args);

// Register your services
builder.Services.AddScoped<IProductService, ProductService>();
builder.Services.AddScoped<IOrderService, OrderService>();
builder.Services.AddSingleton<ICacheService, MemoryCacheService>();
builder.Services.AddTransient<IEmailService, EmailService>();

// Framework services
builder.Services.AddControllers();
builder.Services.AddEndpointsApiExplorer();
builder.Services.AddSwaggerGen();

var app = builder.Build();
```

## Service Lifetimes

The lifetime determines how long a service instance lives and when a new one is created:

        <ul>
            <li>New instance every time</li>
            <li>Lightweight, stateless services</li>
            <li>Most memory allocation</li>
        </ul>
        <code>AddTransient&lt;T&gt;()</code>
    </div>
    <div class="comparison-card">
        <h4>Scoped</h4>
        <ul>
            <li>One instance per HTTP request</li>
            <li>Shared within a single request</li>
            <li>Perfect for DbContext</li>
        </ul>
        <code>AddScoped&lt;T&gt;()</code>
        <span class="tag recommended">Most Common</span>
    </div>
    <div class="comparison-card">
        <h4>Singleton</h4>
        <ul>
            <li>One instance for the app lifetime</li>
            <li>Shared across all requests</li>
            <li>Must be thread-safe</li>
        </ul>
        <code>AddSingleton&lt;T&gt;()</code>
    </div>
</div>

```csharp
// Transient: new instance every time it's requested
builder.Services.AddTransient<IEmailService, EmailService>();

// Scoped: one instance per HTTP request
builder.Services.AddScoped<IProductRepository, ProductRepository>();

// Singleton: one instance for the entire application lifetime
builder.Services.AddSingleton<ICacheService, MemoryCacheService>();
```

## Constructor Injection

The most common way to request a dependency is through the constructor:

```csharp
[ApiController]
[Route("api/[controller]")]
public class OrdersController : ControllerBase
{
    private readonly IOrderService _orderService;
    private readonly ILogger<OrdersController> _logger;

    public OrdersController(
        IOrderService orderService,
        ILogger<OrdersController> logger)
    {
        _orderService = orderService;
        _logger = logger;
    }

    [HttpGet]
    public ActionResult<IEnumerable<Order>> GetAll()
    {
        _logger.LogInformation("Fetching all orders");
        return Ok(_orderService.GetAll());
    }
}
```

## Defining Interfaces and Implementations

A typical service layer follows this pattern:

```csharp
// Interface — defines the contract
public interface IProductService
{
    IEnumerable<Product> GetAll();
    Product? GetById(int id);
    Product Create(CreateProductRequest request);
    bool Update(int id, UpdateProductRequest request);
    bool Delete(int id);
}

// Implementation — contains the logic
public class ProductService : IProductService
{
    private readonly AppDbContext _db;

    public ProductService(AppDbContext db)
    {
        _db = db;
    }

    public IEnumerable<Product> GetAll()
        => _db.Products.ToList();

    public Product? GetById(int id)
        => _db.Products.Find(id);

    public Product Create(CreateProductRequest request)
    {
        var product = request.ToEntity();
        _db.Products.Add(product);
        _db.SaveChanges();
        return product;
    }

    // ... Update and Delete
}
```

## Registering Multiple Implementations

You can register multiple implementations of the same interface:

```csharp
builder.Services.AddScoped<INotificationService, EmailNotificationService>();
builder.Services.AddScoped<INotificationService, SmsNotificationService>();

// Inject all implementations
public class NotificationController : ControllerBase
{
    private readonly IEnumerable<INotificationService> _notifiers;

    public NotificationController(
        IEnumerable<INotificationService> notifiers)
    {
        _notifiers = notifiers;
    }

    [HttpPost("send")]
    public IActionResult SendAll(NotificationRequest request)
    {
        foreach (var notifier in _notifiers)
            notifier.Send(request.Message);

        return Ok();
    }
}
```

## Best Practices

- **Program to interfaces**, not concrete classes
- Use **Scoped** for database contexts and per-request services
- Use **Singleton** only for stateless or thread-safe services
- Keep controllers **thin** — delegate logic to services
- Avoid the **Service Locator** anti-pattern (don't inject `IServiceProvider` unless absolutely necessary)
