## Beyond Request-Response

HTTP and gRPC are synchronous: the caller waits for a response. **Asynchronous messaging** decouples services — the producer sends a message to a broker and moves on. Consumers process messages at their own pace.

This pattern is essential for microservices because it:

- **Removes temporal coupling** — services don't need to be online simultaneously.
- **Absorbs load spikes** — the broker buffers messages when consumers are busy.
- **Enables event-driven architectures** — services react to events instead of polling.

## Message Broker Architecture

```
┌──────────────┐    publish    ┌─────────┐    consume    ┌──────────────────┐
│ OrderService │ ──────────▶   │  Broker  │  ──────────▶ │ InventoryService │
└──────────────┘               │ (queue/  │              └──────────────────┘
                               │  topic)  │  ──────────▶ ┌──────────────────┐
                               └─────────┘              │ NotificationSvc  │
                                                         └──────────────────┘
```

The broker (RabbitMQ, Azure Service Bus, Kafka) stores messages until consumers acknowledge them.

## Defining Messages

Messages are simple data contracts. Keep them small, versioned, and self-contained:

```csharp
// An event — something that happened
public record OrderPlacedEvent(
    Guid OrderId,
    Guid CustomerId,
    List<OrderItemDto> Items,
    decimal TotalAmount,
    DateTime OccurredAt);

public record OrderItemDto(
    int ProductId,
    string ProductName,
    int Quantity,
    decimal UnitPrice);

// A command — an instruction to do something
public record SendInvoiceCommand(
    Guid OrderId,
    Guid CustomerId,
    string Email,
    decimal Amount);
```

## Publishing Messages

A simple abstraction for publishing:

```csharp
public interface IMessagePublisher
{
    Task PublishAsync<T>(T message, CancellationToken ct = default) where T : class;
}

// Usage in OrderService
public class PlaceOrderHandler
{
    private readonly IOrderRepository _orders;
    private readonly IMessagePublisher _publisher;

    public PlaceOrderHandler(IOrderRepository orders, IMessagePublisher publisher)
    {
        _orders = orders;
        _publisher = publisher;
    }

    public async Task HandleAsync(PlaceOrderCommand command, CancellationToken ct)
    {
        var order = Order.Create(command.CustomerId, command.Items);
        await _orders.AddAsync(order, ct);

        // Publish event — consumers handle the rest
        await _publisher.PublishAsync(new OrderPlacedEvent(
            order.Id, order.CustomerId, order.Items.ToDto(),
            order.Total, DateTime.UtcNow), ct);
    }
}
```

## Consuming Messages

```csharp
public interface IMessageConsumer<T> where T : class
{
    Task HandleAsync(T message, CancellationToken ct);
}

// InventoryService reacts to OrderPlaced
public class OrderPlacedConsumer : IMessageConsumer<OrderPlacedEvent>
{
    private readonly IStockRepository _stock;
    private readonly ILogger<OrderPlacedConsumer> _logger;

    public OrderPlacedConsumer(IStockRepository stock, ILogger<OrderPlacedConsumer> logger)
    {
        _stock = stock;
        _logger = logger;
    }

    public async Task HandleAsync(OrderPlacedEvent message, CancellationToken ct)
    {
        foreach (var item in message.Items)
        {
            await _stock.ReserveAsync(item.ProductId, item.Quantity, ct);
            _logger.LogInformation("Reserved {Qty} of product {ProductId} for order {OrderId}",
                item.Quantity, item.ProductId, message.OrderId);
        }
    }
}
```

## Idempotent Consumers

Messages can be delivered more than once (at-least-once delivery). Consumers must handle duplicates safely:

```csharp
public class OrderPlacedConsumer : IMessageConsumer<OrderPlacedEvent>
{
    private readonly IProcessedMessages _processed;
    private readonly IStockRepository _stock;

    public async Task HandleAsync(OrderPlacedEvent message, CancellationToken ct)
    {
        // Check if we've already processed this message
        if (await _processed.ExistsAsync(message.OrderId, ct))
            return;

        foreach (var item in message.Items)
            await _stock.ReserveAsync(item.ProductId, item.Quantity, ct);

        // Mark as processed
        await _processed.AddAsync(message.OrderId, ct);
    }
}
```

## When to Use Messaging vs HTTP

| Scenario | Use |
|---|---|
| Need an immediate response | HTTP / gRPC |
| Fire-and-forget action | Messaging |
| Notify multiple services | Publish/subscribe |
| Absorb traffic spikes | Messaging |
| Real-time request-response | HTTP / gRPC |

## Best Practices

- **Use events for notifications**, commands for actions
- **Make consumers idempotent** — handle duplicate messages gracefully
- **Include all needed data** in the message to avoid callbacks
- **Version your message contracts** — add fields, don't remove them
- **Monitor queue depth** — growing queues indicate consumers can't keep up
- **Use dead-letter queues** for messages that repeatedly fail
