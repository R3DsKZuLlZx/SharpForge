## Domain-Driven Design for Microservices

Domain-Driven Design (DDD) provides the conceptual tools to find good microservice boundaries. You don't need to adopt all of DDD, but **bounded contexts**, **aggregates**, and **ubiquitous language** are essential for microservices done right.

## Bounded Contexts

A **bounded context** is an explicit boundary within which a particular domain model is defined and consistent. The same real-world concept can mean different things in different contexts.

Each bounded context gets its own model, its own database, and its own service. They communicate through well-defined contracts, not shared classes.

## Ubiquitous Language

Within a bounded context, developers and domain experts use the **same terms** in conversation, documentation, and code. If the business calls it an "Order," the code calls it `Order` — not `PurchaseRequest` or `Transaction`.

```csharp
// ✅ GOOD: Code mirrors the domain language
public class Order
{
    public OrderId Id { get; private set; }
    public CustomerId CustomerId { get; private set; }
    public List<OrderLine> Lines { get; private set; } = [];
    public OrderStatus Status { get; private set; }

    public void Place()
    {
        if (Lines.Count == 0)
            throw new InvalidOperationException("Cannot place an empty order.");
        Status = OrderStatus.Placed;
    }
}

// ❌ BAD: Generic terms that don't match the business
public class TransactionEntity
{
    public int TransId { get; set; }
    public int CustRef { get; set; }
    public List<LineItemDto> Items { get; set; } = [];
    public int StateCode { get; set; }
}
```

## Aggregates

An **aggregate** is a cluster of domain objects treated as a single unit for data changes. It has a **root entity** that controls access and enforces invariants.

<div class="info-box">
    <div class="info-box-header"><svg width="20" height="20" viewBox="0 0 24 24" fill="none" stroke="currentColor" stroke-width="2"><circle cx="12" cy="12" r="10"/><line x1="12" y1="16" x2="12" y2="12"/><line x1="12" y1="8" x2="12.01" y2="8"/></svg><span>Aggregate Rules</span></div>
    <ul>
        <li>External objects can only reference the <strong>aggregate root</strong>.</li>
        <li>All changes go through the root — it guards the invariants.</li>
        <li>One aggregate = one transaction boundary. Don't span aggregates in a single transaction.</li>
    </ul>
</div>

```csharp
// Order is the aggregate root
public class Order
{
    public OrderId Id { get; private set; }
    private readonly List<OrderLine> _lines = [];
    public IReadOnlyList<OrderLine> Lines => _lines.AsReadOnly();

    public void AddLine(ProductId productId, int quantity, decimal unitPrice)
    {
        if (quantity <= 0)
            throw new ArgumentException("Quantity must be positive.");

        var existing = _lines.FirstOrDefault(l => l.ProductId == productId);
        if (existing is not null)
            existing.IncreaseQuantity(quantity);
        else
            _lines.Add(new OrderLine(productId, quantity, unitPrice));
    }

    public decimal Total => _lines.Sum(l => l.Subtotal);
}

// OrderLine is an entity inside the Order aggregate
public class OrderLine
{
    public ProductId ProductId { get; private set; }
    public int Quantity { get; private set; }
    public decimal UnitPrice { get; private set; }
    public decimal Subtotal => Quantity * UnitPrice;

    internal OrderLine(ProductId productId, int quantity, decimal unitPrice)
    {
        ProductId = productId;
        Quantity = quantity;
        UnitPrice = unitPrice;
    }

    internal void IncreaseQuantity(int amount) => Quantity += amount;
}
```

## Value Objects

**Value objects** are immutable and defined by their properties, not an identity. Use them for concepts like money, addresses, or IDs:

```csharp
public record Money(decimal Amount, string Currency)
{
    public static Money USD(decimal amount) => new(amount, "USD");
    public Money Add(Money other)
    {
        if (Currency != other.Currency)
            throw new InvalidOperationException("Cannot add different currencies.");
        return this with { Amount = Amount + other.Amount };
    }
}

public record Address(string Street, string City, string State, string ZipCode);
```

## Domain Events

When something significant happens in a bounded context, raise a **domain event**. Other services can react to it asynchronously.

```csharp
public record OrderPlacedEvent(
    Guid OrderId,
    Guid CustomerId,
    decimal TotalAmount,
    DateTime PlacedAt);

public class Order
{
    private readonly List<IDomainEvent> _events = [];
    public IReadOnlyList<IDomainEvent> DomainEvents => _events.AsReadOnly();

    public void Place()
    {
        Status = OrderStatus.Placed;
        _events.Add(new OrderPlacedEvent(Id.Value, CustomerId.Value, Total, DateTime.UtcNow));
    }

    public void ClearEvents() => _events.Clear();
}
```

## Context Mapping

When bounded contexts interact, you need a **context map** that defines the relationship:

- **Partnership** — Two teams cooperate and evolve together.
- **Customer-Supplier** — Upstream supplies data; downstream consumes it.
- **Anti-Corruption Layer (ACL)** — Downstream translates the upstream model to protect its own model.

```csharp
// Anti-Corruption Layer: translating the external Payments model
// into our internal Order domain model
public class PaymentAclService
{
    private readonly IPaymentGateway _gateway;

    public PaymentAclService(IPaymentGateway gateway)
        => _gateway = gateway;

    public async Task<PaymentResult> ChargeAsync(Order order)
    {
        // Translate our domain model to the external API
        var request = new ExternalChargeRequest
        {
            ReferenceId = order.Id.Value.ToString(),
            AmountCents = (int)(order.Total * 100),
            Currency = "usd"
        };

        var response = await _gateway.ChargeAsync(request);

        // Translate the response back to our domain
        return new PaymentResult(response.Succeeded, response.TransactionId);
    }
}
```

## Best Practices

- **One bounded context = one microservice** — this is the primary alignment heuristic
- **Keep aggregates small** — large aggregates cause contention and performance issues
- **Reference other aggregates by ID**, not by direct object reference
- **Raise domain events** for cross-context communication instead of synchronous calls
- **Don't share entity classes** between services — each context has its own model
