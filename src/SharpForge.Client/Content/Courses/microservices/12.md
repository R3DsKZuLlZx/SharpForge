## Own Your Data

The **database-per-service** pattern is a core microservices principle: each service has its own private data store that no other service can access directly. Other services interact with data only through the service's API.

## Why Separate Databases?

<div class="comparison-grid">
    <div class="comparison-card">
        <h4>Shared Database</h4>
        <ul>
            <li>Tight coupling between services</li>
            <li>Schema changes break multiple services</li>
            <li>Can't scale databases independently</li>
            <li>Easy cross-service queries (joins)</li>
        </ul>
    </div>
    <div class="comparison-card">
        <h4>Database per Service</h4>
        <ul>
            <li>Loose coupling</li>
            <li>Independent schema evolution</li>
            <li>Scale each database separately</li>
            <li>Cross-service queries are harder</li>
        </ul>
        <span class="tag recommended">Recommended</span>
    </div>
</div>

## Polyglot Persistence

Different services can use different database technologies based on their needs:

```
┌─────────────────┐     ┌─────────────────┐     ┌─────────────────┐
│  Order Service  │     │ Catalog Service │     │ Search Service  │
│                 │     │                 │     │                 │
│  SQL Server     │     │  PostgreSQL     │     │  Elasticsearch  │
│  (transactions) │     │  (relational)   │     │  (full-text)    │
└─────────────────┘     └─────────────────┘     └─────────────────┘

┌─────────────────┐     ┌─────────────────┐
│  Cart Service   │     │ Analytics Svc   │
│                 │     │                 │
│  Redis          │     │  ClickHouse     │
│  (fast k/v)     │     │  (OLAP)         │
└─────────────────┘     └─────────────────┘
```

## Service Configuration

Each service configures its own database connection:

```csharp
// OrderService/Program.cs
builder.Services.AddDbContext<OrderDbContext>(options =>
    options.UseSqlServer(builder.Configuration.GetConnectionString("OrderDb")));

// InventoryService/Program.cs
builder.Services.AddDbContext<InventoryDbContext>(options =>
    options.UseNpgsql(builder.Configuration.GetConnectionString("InventoryDb")));
```

```yaml
# docker-compose.yml
services:
  order-service:
    environment:
      - ConnectionStrings__OrderDb=Server=order-db;Database=orders;...
  inventory-service:
    environment:
      - ConnectionStrings__InventoryDb=Host=inventory-db;Database=inventory;...

  order-db:
    image: mcr.microsoft.com/mssql/server:2022-latest
  inventory-db:
    image: postgres:16
```

## Handling Cross-Service Queries

Without shared tables, you can't use SQL joins across services. There are several strategies:

### API Composition

The client (or a gateway) calls multiple services and combines the results:

```csharp
public class OrderDetailsComposer
{
    private readonly OrderClient _orders;
    private readonly CustomerClient _customers;

    public async Task<OrderDetailsDto> GetOrderDetailsAsync(Guid orderId)
    {
        var order = await _orders.GetAsync(orderId);
        var customer = await _customers.GetAsync(order.CustomerId);

        return new OrderDetailsDto
        {
            OrderId = order.Id,
            CustomerName = customer.Name,
            Items = order.Items,
            Total = order.Total
        };
    }
}
```

### Data Duplication via Events

Consume events and store a local copy of data you need for queries:

```csharp
// OrderService consumes CustomerUpdated events and stores
// a local read model with just the fields it needs
public class CustomerUpdatedConsumer : IConsumer<CustomerUpdatedEvent>
{
    private readonly OrderDbContext _db;

    public async Task Consume(ConsumeContext<CustomerUpdatedEvent> context)
    {
        var msg = context.Message;
        var local = await _db.CustomerReadModels.FindAsync(msg.CustomerId);

        if (local is null)
        {
            _db.CustomerReadModels.Add(new CustomerReadModel
            {
                CustomerId = msg.CustomerId,
                Name = msg.Name,
                Email = msg.Email
            });
        }
        else
        {
            local.Name = msg.Name;
            local.Email = msg.Email;
        }

        await _db.SaveChangesAsync();
    }
}
```

Now the OrderService can join against its local `CustomerReadModels` table for queries.

<div class="warning-box">
    <div class="warning-box-header"><span>⚠️ Trade-Off</span></div>
    <p>Data duplication means data can be <strong>temporarily stale</strong>. The local copy updates when the event is consumed, which may lag behind the source. This is <strong>eventual consistency</strong> — acceptable for reads, but not for business-critical decisions.</p>
</div>

## Migrations per Service

Each service manages its own database schema migrations independently:

```bash
# OrderService migrations
cd OrderService
dotnet ef migrations add AddShippingAddress
dotnet ef database update

# InventoryService migrations (completely independent)
cd InventoryService
dotnet ef migrations add AddWarehouseLocation
dotnet ef database update
```

## Best Practices

- **Never let a service read another service's database directly**
- Use **events** to propagate data that other services need for local queries
- Accept **eventual consistency** for read models; use synchronous calls only when strong consistency is required
- Start with **one database technology** and separate databases; introduce polyglot persistence only when justified
- Each service owns its **migrations** and can evolve its schema independently
