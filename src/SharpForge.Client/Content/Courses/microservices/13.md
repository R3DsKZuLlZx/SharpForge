## Distributed Transactions Without 2PC

In a monolith, a single database transaction can span multiple operations. In microservices, each service has its own database — there's no shared transaction. The **Saga pattern** manages multi-service business processes by breaking them into a sequence of local transactions, each with a compensating action for rollback.

## Choreography vs Orchestration

<div class="comparison-grid">
    <div class="comparison-card">
        <h4>Choreography</h4>
        <p>Each service publishes events; other services react.</p>
        <ul>
            <li>No central coordinator</li>
            <li>Simple for few steps</li>
            <li>Hard to track overall state</li>
            <li>Can become tangled</li>
        </ul>
    </div>
    <div class="comparison-card">
        <h4>Orchestration</h4>
        <p>A central saga orchestrator tells each service what to do.</p>
        <ul>
            <li>Clear workflow logic</li>
            <li>Easier to debug</li>
            <li>Central point of failure</li>
            <li>Better for complex flows</li>
        </ul>
        <span class="tag recommended">Recommended for complex flows</span>
    </div>
</div>

## Choreography Example

An order placement saga using events:

```
OrderService                 InventoryService              PaymentService
    │                              │                              │
    │── OrderPlaced ──────────────▶│                              │
    │                              │── StockReserved ────────────▶│
    │                              │                              │── PaymentCharged ──▶ ✅
    │                              │                              │
    │                              │◀── PaymentFailed ───────────│
    │                              │── StockReleased             │
    │◀── StockReleased             │                              │
    │── OrderCancelled             │                              │
```

Each service listens for events and reacts:

```csharp
// InventoryService reacts to OrderPlaced
public class OrderPlacedConsumer : IConsumer<OrderPlacedEvent>
{
    private readonly IStockRepository _stock;
    private readonly IPublishEndpoint _publisher;

    public async Task Consume(ConsumeContext<OrderPlacedEvent> context)
    {
        var msg = context.Message;
        var reserved = await _stock.TryReserveAsync(msg.ProductId, msg.Quantity);

        if (reserved)
        {
            await _publisher.Publish(new StockReservedEvent
            {
                OrderId = msg.OrderId,
                ProductId = msg.ProductId,
                Quantity = msg.Quantity
            });
        }
        else
        {
            await _publisher.Publish(new StockReservationFailedEvent
            {
                OrderId = msg.OrderId,
                Reason = "Insufficient stock"
            });
        }
    }
}
```

## Orchestration Example

A saga orchestrator manages the workflow:

```csharp
public class PlaceOrderSaga : MassTransitStateMachine<PlaceOrderSagaState>
{
    public State ReservingStock { get; private set; } = null!;
    public State ChargingPayment { get; private set; } = null!;
    public State Completed { get; private set; } = null!;
    public State Failed { get; private set; } = null!;

    public Event<OrderPlacedEvent> OrderPlaced { get; private set; } = null!;
    public Event<StockReservedEvent> StockReserved { get; private set; } = null!;
    public Event<PaymentChargedEvent> PaymentCharged { get; private set; } = null!;
    public Event<PaymentFailedEvent> PaymentFailed { get; private set; } = null!;

    public PlaceOrderSaga()
    {
        InstanceState(x => x.CurrentState);

        Event(() => OrderPlaced, x => x.CorrelateById(ctx => ctx.Message.OrderId));
        Event(() => StockReserved, x => x.CorrelateById(ctx => ctx.Message.OrderId));
        Event(() => PaymentCharged, x => x.CorrelateById(ctx => ctx.Message.OrderId));
        Event(() => PaymentFailed, x => x.CorrelateById(ctx => ctx.Message.OrderId));

        Initially(
            When(OrderPlaced)
                .Then(ctx => ctx.Saga.OrderId = ctx.Message.OrderId)
                .Send(new Uri("queue:reserve-stock"), ctx =>
                    new ReserveStockCommand { OrderId = ctx.Message.OrderId })
                .TransitionTo(ReservingStock));

        During(ReservingStock,
            When(StockReserved)
                .Send(new Uri("queue:charge-payment"), ctx =>
                    new ChargePaymentCommand { OrderId = ctx.Saga.OrderId })
                .TransitionTo(ChargingPayment));

        During(ChargingPayment,
            When(PaymentCharged)
                .TransitionTo(Completed)
                .Finalize(),
            When(PaymentFailed)
                .Send(new Uri("queue:release-stock"), ctx =>
                    new ReleaseStockCommand { OrderId = ctx.Saga.OrderId })
                .TransitionTo(Failed)
                .Finalize());
    }
}

public class PlaceOrderSagaState : SagaStateMachineInstance
{
    public Guid CorrelationId { get; set; }
    public string CurrentState { get; set; } = "";
    public Guid OrderId { get; set; }
}
```

Register the saga:

```csharp
builder.Services.AddMassTransit(x =>
{
    x.AddSagaStateMachine<PlaceOrderSaga, PlaceOrderSagaState>()
        .InMemoryRepository(); // Use Redis or EF Core for production

    x.UsingRabbitMq((context, cfg) =>
    {
        cfg.Host("rabbitmq");
        cfg.ConfigureEndpoints(context);
    });
});
```

## Compensating Actions

Every forward step needs a compensating action to undo its effect:

| Step | Action | Compensation |
|---|---|---|
| 1 | Reserve stock | Release stock |
| 2 | Charge payment | Refund payment |
| 3 | Create shipment | Cancel shipment |

<div class="warning-box">
    <div class="warning-box-header"><span>⚠️ Important</span></div>
    <p>Compensating actions don't "roll back" — they apply a new action that reverses the effect. A refund is a new transaction, not a deletion. Design compensations to be <strong>idempotent</strong>.</p>
</div>

## Best Practices

- Use **choreography** for simple, linear flows (2–3 steps)
- Use **orchestration** for complex flows with branching or many steps
- **Every step must have a compensating action** — plan for failure from the start
- Make all saga steps and compensations **idempotent**
- **Persist saga state** to a durable store (EF Core, Redis) — in-memory is only for development
- Use **correlation IDs** (e.g., `OrderId`) to link events belonging to the same saga
