## Why Containers?

Microservices need a consistent, lightweight way to package and run each service. **Docker** containers solve the "it works on my machine" problem by bundling your application, its runtime, and all dependencies into a single, portable unit.

## Images and Containers

- An **image** is a read-only template that contains your app, its dependencies, and instructions on how to run it.
- A **container** is a running instance of an image. You can run many containers from the same image.

```bash
# Pull an image from Docker Hub
docker pull mcr.microsoft.com/dotnet/aspnet:9.0

# Run a container from the image
docker run -d --name my-app -p 8080:8080 my-app-image

# List running containers
docker ps

# View container logs
docker logs my-app

# Stop and remove a container
docker stop my-app
docker rm my-app
```

## Anatomy of a Dockerfile

A `Dockerfile` contains the instructions to build an image:

```dockerfile
# Start from a base image
FROM mcr.microsoft.com/dotnet/aspnet:9.0

# Set the working directory inside the container
WORKDIR /app

# Copy published files into the container
COPY ./publish .

# Expose the port the app listens on
EXPOSE 8080

# Define the command to run the app
ENTRYPOINT ["dotnet", "MyService.dll"]
```

Each instruction creates a **layer**. Docker caches layers, so unchanged layers aren't rebuilt — this makes subsequent builds fast.

## Essential Docker Commands

```bash
# Build an image from a Dockerfile
docker build -t my-app:1.0 .

# List local images
docker images

# Run with environment variables
docker run -d -e "ASPNETCORE_ENVIRONMENT=Production" -p 8080:8080 my-app:1.0

# Execute a command inside a running container
docker exec -it my-app bash

# Remove an image
docker rmi my-app:1.0

# Clean up unused resources
docker system prune
```

## Port Mapping

Containers are isolated. To access a service from outside, you map a **host port** to a **container port**:

```bash
# Map host port 5000 to container port 8080
docker run -d -p 5000:8080 my-app

# Now access the app at http://localhost:5000
```

## Volumes and Data Persistence

Containers are **ephemeral** — when they stop, any data written inside is lost. Use **volumes** to persist data:

```bash
# Create a named volume
docker volume create my-data

# Mount it into a container
docker run -d -v my-data:/app/data my-app

# Bind mount a host directory (useful for development)
docker run -d -v $(pwd)/config:/app/config my-app
```

## Networking Basics

Docker creates a default bridge network. Containers on the same network can communicate using container names as hostnames:

```bash
# Create a custom network
docker network create my-net

# Run containers on the same network
docker run -d --name order-service --network my-net order-service-image
docker run -d --name inventory-service --network my-net inventory-service-image

# order-service can now reach inventory-service at http://inventory-service:8080
```

## Best Practices

- Use **specific image tags** (e.g., `aspnet:9.0`) instead of `latest` for reproducibility
- Keep images **small** — use slim or Alpine-based images when possible
- **Don't run as root** inside containers — create a non-root user
- Use `.dockerignore` to exclude `bin/`, `obj/`, and other unnecessary files
- **One process per container** — don't run multiple services in one container
