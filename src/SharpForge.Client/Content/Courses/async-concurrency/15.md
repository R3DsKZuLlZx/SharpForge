## ❌ Pitfall 1: async void

Illustrates why `async void` is dangerous (exceptions lost and cannot be awaited), and shows correct patterns and the exception where async void is acceptable (event handlers).

```csharp
// ❌ BAD - exceptions are lost, can't be awaited
async void DoWork()
{
    await Task.Delay(100);
    throw new Exception("Lost forever!");
}

// ✅ GOOD - return Task
async Task DoWorkAsync()
{
    await Task.Delay(100);
}

// Exception: Event handlers CAN use async void
button.Click += async (s, e) => await HandleClickAsync();
```

## ❌ Pitfall 2: Blocking on Async (Deadlock!)

Examples that cause deadlocks when blocking on async code in contexts with synchronization contexts (UI/ASP.NET classic); advocate "async all the way" instead.

```csharp
// ❌ DEADLOCK in UI/ASP.NET apps!
public string GetData()
{
    return GetDataAsync().Result;  // Blocks!
}

// ❌ Also deadlock
public string GetData()
{
    return GetDataAsync().GetAwaiter().GetResult();
}

// ✅ GOOD - async all the way
public async Task<string> GetDataAsync()
{
    return await httpClient.GetStringAsync(url);
}
```

## ❌ Pitfall 3: Not Using ConfigureAwait

Use `ConfigureAwait(false)` in library code to avoid capturing the synchronization context and improve compatibility/performance across hosting models.

```csharp
// In library code, always use ConfigureAwait(false)
public async Task<Data> LibraryMethodAsync()
{
    // Don't capture sync context
    var result = await httpClient.GetAsync(url).ConfigureAwait(false);
    return await result.Content.ReadFromJsonAsync<Data>().ConfigureAwait(false);
}
```

## ❌ Pitfall 4: Not Passing CancellationToken

Show why accepting and passing cancellation tokens is important for cooperative cancellation and resource management.

```csharp
// ❌ BAD - ignores cancellation
public async Task ProcessAsync()
{
    await httpClient.GetStringAsync(url);  // Can't cancel!
}

// ✅ GOOD - accept and pass token
public async Task ProcessAsync(CancellationToken ct = default)
{
    await httpClient.GetStringAsync(url, ct);
}
```

## ❌ Pitfall 5: Using Task.Run for I/O

Don't offload I/O-bound work to the thread pool with `Task.Run`, instead await async I/O directly to avoid wasting threads.

```csharp
// ❌ BAD - wastes a thread pool thread
var data = await Task.Run(() => httpClient.GetStringAsync(url));

// ✅ GOOD - just await directly
var data = await httpClient.GetStringAsync(url);
```
