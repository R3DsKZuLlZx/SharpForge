## Evolve Without Breaking

As your API grows, you'll need to make breaking changes — new fields, different response shapes, removed endpoints. API versioning lets you make these changes without disrupting existing clients. In this lesson, you'll learn the common versioning strategies.

## Why Version Your API?

Without versioning, any change to a response shape can break every client:

```csharp
// v1: Clients expect this shape
{ "name": "Laptop", "price": 999.99 }

// v2: You add a field — safe, but renaming or removing breaks clients
{ "productName": "Laptop", "price": 999.99, "category": "Electronics" }
```

Versioning lets both shapes coexist so clients can migrate at their own pace.

## Setting Up API Versioning

Install the NuGet package:

```bash
dotnet add package Asp.Versioning.Mvc
dotnet add package Asp.Versioning.Mvc.ApiExplorer
```

Configure versioning in `Program.cs`:

```csharp
builder.Services.AddApiVersioning(options =>
{
    options.DefaultApiVersion = new ApiVersion(1, 0);
    options.AssumeDefaultVersionWhenUnspecified = true;
    options.ReportApiVersions = true;  // Adds version headers to responses
    options.ApiVersionReader = new UrlSegmentApiVersionReader();
})
.AddApiExplorer(options =>
{
    options.GroupNameFormat = "'v'VVV";
    options.SubstituteApiVersionInUrl = true;
});
```

## URL Segment Versioning

The most common and visible approach — the version is part of the URL:

```csharp
[ApiController]
[Route("api/v{version:apiVersion}/products")]
[ApiVersion("1.0")]
public class ProductsV1Controller : ControllerBase
{
    [HttpGet]
    public IActionResult GetAll()
    {
        var products = new[]
        {
            new { Name = "Laptop", Price = 999.99m }
        };
        return Ok(products);
    }
}

[ApiController]
[Route("api/v{version:apiVersion}/products")]
[ApiVersion("2.0")]
public class ProductsV2Controller : ControllerBase
{
    [HttpGet]
    public IActionResult GetAll()
    {
        var products = new[]
        {
            new { Name = "Laptop", Price = 999.99m,
                  Description = "High-performance laptop",
                  Category = "Electronics" }
        };
        return Ok(products);
    }
}
```

```bash
GET /api/v1/products  → Returns simple product list
GET /api/v2/products  → Returns extended product list
```

## Query String Versioning

The version is passed as a query parameter:

```csharp
builder.Services.AddApiVersioning(options =>
{
    options.ApiVersionReader = new QueryStringApiVersionReader("api-version");
});
```

```bash
GET /api/products?api-version=1.0
GET /api/products?api-version=2.0
```

## Header Versioning

The version is sent in a custom HTTP header:

```csharp
builder.Services.AddApiVersioning(options =>
{
    options.ApiVersionReader = new HeaderApiVersionReader("X-Api-Version");
});
```

```bash
GET /api/products
X-Api-Version: 2.0
```

## Combining Version Readers

You can support multiple strategies simultaneously:

```csharp
builder.Services.AddApiVersioning(options =>
{
    options.ApiVersionReader = ApiVersionReader.Combine(
        new UrlSegmentApiVersionReader(),
        new QueryStringApiVersionReader("api-version"),
        new HeaderApiVersionReader("X-Api-Version"));
});
```

## Deprecating Versions

Mark old versions as deprecated to signal that clients should migrate:

```csharp
[ApiController]
[Route("api/v{version:apiVersion}/products")]
[ApiVersion("1.0", Deprecated = true)]  // Marked deprecated
public class ProductsV1Controller : ControllerBase
{
    // Still works, but response headers indicate deprecation
    // api-deprecated-versions: 1.0
    // api-supported-versions: 2.0
}
```

When `ReportApiVersions` is enabled, ASP.NET Core adds `api-supported-versions` and `api-deprecated-versions` headers to every response so clients can discover available versions.

## Best Practices

- Choose **one primary versioning strategy** and be consistent
- Use **URL segment versioning** for public-facing APIs
- Set a **default version** so existing clients don't break
- **Deprecate** old versions before removing them
- Document version changes in a **changelog** or migration guide
- Version from **day one** — it's much harder to add later
